GOAL: BUILD "GBA WRITER" — A GBA-NATIVE PLAIN-TEXT WRITER / DIARY
=======================================================================

You are an autonomous coding agent. Implement a new Game Boy Advance homebrew application called "GBA Writer".

The project should be based technically and visually on:

https://github.com/Xinon232/gbareader

Use the current GBAReader codebase as the architectural/font/UI foundation rather than starting over. Reuse/adapt its proven Supercard SD + FatFS path, Butano setup, menu style, font assets/rendering, and text rendering architecture where appropriate.

The finished app is NOT an e-reader with editing bolted on. It is a focused plain-text writer/editor with:

- a custom controller-native typing system
- fast diary-file creation
- safe saving
- file loading
- cursor navigation
- international Latin-character support
- no on-screen QWERTY keyboard

Do not redesign the controls or UX described below unless a change is technically unavoidable.

If something is ambiguous at implementation level, choose the simplest robust behavior that preserves the stated UX.

The control system is deliberate and must be implemented as explicit input state machines rather than inferred afterward from produced text.

4. NEW FILE / DIARY DATE LOGIC
=======================================================================

Diary filenames use exactly:

DDMMYYYY.txt

Example:

21102026.txt

A valid diary filename must:

- contain exactly 8 decimal digits before ".txt"
- use DDMMYYYY interpretation
- represent a real valid Gregorian calendar date
- be treated case-insensitively for the .txt extension if necessary
- newly created files should use lowercase ".txt"


A) SCAN FOR EXISTING DATED FILES
--------------------------------

Scan /gbawriter/ for all filenames matching a valid DDMMYYYY.txt diary filename.

Parse them as actual dates.

Find the CHRONOLOGICALLY LATEST valid date.

Do NOT determine the latest file through raw filename/string sorting.

Example:

12121990.txt
21102001.txt

Latest date:

21 October 2001

Therefore the proposed next file is:

22102001.txt


B) IF AT LEAST ONE VALID DATED FILE EXISTS
-------------------------------------------

Preset the New File date picker to:

latest valid diary date + 1 calendar day

Examples:

21102026 -> 22102026
31102026 -> 01112026
31122026 -> 01012027
28022028 -> 29022028
28022027 -> 01032027

Use correct Gregorian leap-year/calendar arithmetic.


C) IF NO VALID DATED FILE EXISTS
--------------------------------

Open the date picker and require the user to choose the initial date manually.

Do NOT use the custom typewriter controls in the date picker.

The date picker uses conventional menu controls.

Suggested presentation:

NEW FILE

DAY    21
MONTH  10
YEAR   2026

A: CREATE
B: BACK

Behavior:

- Left/Right switches selected field: DAY / MONTH / YEAR
- Up/Down increments/decrements selected field
- A attempts to create the proposed DDMMYYYY.txt file
- B cancels and returns to main menu

Implement date validity cleanly.

The user must not be able to create impossible dates such as:

31 February

Either clamp fields appropriately or reject invalid dates with a clear message.


D) NEVER OVERWRITE FROM NEW FILE
--------------------------------

NEW FILE must NEVER overwrite an existing file.

Before creating any file, check whether that exact destination filename already exists.

If it exists:

- do not overwrite it
- do not truncate it
- do not delete it
- do not silently rename it
- do not create suffixes such as "_2"

Show a warning such as:

FILE ALREADY EXISTS

21102001.txt

CHOOSE ANOTHER DATE

A: OK

After acknowledgement, return to the date picker with the user's proposed date still present.

The user can then change it.

This protection applies even if the automatic preset should theoretically have produced a free filename.

Always perform the final existence check.

The automatic preset is always based on:

latest existing valid dated file + exactly one calendar day

10. SPECIAL SAME-SESSION LETTER TRANSFORMATIONS
=======================================================================

Two letters are not mapped directly:

g
v

They are generated through repeated third-letter input while the SAME relevant direction group remains continuously held.

These are INPUT-SESSION transformations.

They are NOT global text substitutions.


G FROM JJ
---------

DOWN + R normally produces:

j

If the user holds DOWN continuously and presses R twice before releasing DOWN:

hold DOWN
-> press R
-> press R
-> release DOWN

result:

g

Conceptually:

jj -> g

but only inside one continuous DOWN-group input session.

Therefore:

hold DOWN
R
R
release

= g

but:

DOWN + R
release DOWN
DOWN + R
release DOWN

= jj

Literal "jj" must remain typable.

User speed is irrelevant.

There is NO timing threshold.

The defining condition is:

DOWN was never released between the first and second R press.


V FROM WW
---------

L + DOWN + R normally produces:

w

If the user continuously holds the relevant group and presses R twice:

hold L + DOWN
-> press R
-> press R
-> release group

result:

v

Conceptually:

ww -> v

Again this is session-based.

If the group is released between inputs:

L + DOWN + R
release
L + DOWN + R
release

= ww

Literal "ww" must remain typable.

Model these group sessions explicitly.

12. CAPITALIZATION — R ALONE
=======================================================================

R is both:

1. the third-letter key when a direction letter group is active
2. the capitalization key when pressed by itself

These roles must be disambiguated explicitly.


R INSIDE A LETTER GROUP
-----------------------

Examples:

UP + R
= c

RIGHT + R
= f

L + RIGHT + R
= s

In these cases R is the third-letter selector.

It must NOT trigger Shift or Caps Lock.


R ALONE: SINGLE PRESS
---------------------

A short isolated R press arms:

SHIFT NEXT ALPHABETIC CHARACTER

If normal mode is lowercase:

R once
-> next alphabetic character uppercase
-> then automatically return to lowercase

Example:

R
RIGHT + A

result:

E

instead of:

e


SHIFT WHILE CAPS LOCK IS ACTIVE
-------------------------------

If Caps Lock is active:

R once
-> next alphabetic character lowercase
-> after that character, return automatically to Caps Lock uppercase behavior


PUNCTUATION / NUMBERS
---------------------

One-character Shift applies to the next alphabetic character.

Numbers and punctuation do NOT consume the one-character Shift state.


R ALONE: DOUBLE PRESS
---------------------

Two isolated R presses in succession toggle Caps Lock.

Caps off:

R
R

-> CAPS ON

Caps on:

R
R

-> CAPS OFF


DISAMBIGUATION
--------------

R capitalization recognition applies only when:

- no D-pad letter group is active
- SELECT is not held
- START is not held
- R is not functioning as the final selector of an L-layer letter chord

Repeated R inside a continuously held DOWN group must continue to support:

JJ -> G

Repeated R inside a continuously held L+DOWN group must continue to support:

WW -> V

Those cases are NOT Caps Lock double presses.


RESPONSIVE DOUBLE-PRESS MODEL
-----------------------------

Do not make R feel laggy.

Recommended behavior:

- first short isolated R release immediately arms one-character Shift
- if a second qualifying isolated R press occurs within a short configurable double-press window before an alphabetic character is typed, reinterpret the pair as a Caps Lock toggle
- clear the one-shot Shift state when the double press becomes a Caps Lock toggle

If Caps Lock was already active:

- first isolated R may temporarily arm inverse one-character Shift
- a qualifying second isolated R within the double-press window converts the pair into Caps Lock OFF
- clear the temporary one-character Shift state

Keep the double-press timing constant centralized/configurable.


VISUAL STATE
------------

Show a small unobtrusive indicator:

↑

when one-letter Shift is armed.

Show:

CAPS

when Caps Lock is active.

Do not obscure document text.


=======================================================================
13. START — ENTER + EDITOR COMMAND MODIFIER
=======================================================================

START has deferred behavior.

This is deliberately different from SELECT.

SELECT creates a provisional text character immediately.

START does NOT perform its default Enter action until START is released and the system knows no START command was used.


START ALONE
-----------

START down:

do nothing yet

START released without any START command having been used:

insert Enter / newline


Conceptual state model:

START down
-> enter pending START-command state
-> command_used = false

START released
if command_used == false:
    insert newline
else:
    do nothing


START + COMMAND
---------------

While START remains held:

START + LEFT
= move insertion caret one logical position left

START + RIGHT
= move insertion caret one logical position right

START + UP
= move caret to closest horizontal position in visual row above

START + DOWN
= move caret to closest horizontal position in visual row below

START + L
= previous page / viewport page

START + R
= next page / viewport page

START + A
= save current text to current file

START + B
= save current text and return to main menu


Any successful recognition of one of these START combinations sets:

command_used = true

Therefore releasing START afterward must NOT also insert a newline.


Example:

hold START
press A
-> SAVE

release START
-> nothing

NOT:

SAVE
+ accidental newline


START COMMAND PRECEDENCE
------------------------

While START is held:

- do not trigger normal letter typing
- do not trigger R Shift/Caps
- do not trigger A Space
- do not trigger B Backspace
- do not trigger L second-letter layer
- do not trigger normal D-pad typing groups

START command mode has higher priority.


CURSOR MOVEMENT
---------------

START + LEFT/RIGHT moves through logical displayed characters/codepoints.

START + UP/DOWN moves through VISUAL rows, including soft-wrapped rows.

Up/down movement should preserve the intended horizontal column as naturally as practical.

Allow reasonable held-key repetition for navigation.

Do not let navigation create characters.


SAVE + MENU
-----------

START + B means:

save current text
then return to main menu

Only leave the editor after the save succeeds.

If save fails:

- display the failure clearly
- remain in editor
- preserve text
- do not falsely report success


=======================================================================
14. SELECT — PROVISIONAL SPECIAL-CHARACTER SYSTEM
=======================================================================

SELECT is a live/provisional special-character modifier.

This is a central part of the keyboard.

It is NOT simply a normal held modifier.

PRESS SELECT:

SELECT down
-> immediately insert "."
-> record the position of that just-inserted character
-> mark that exact character as PROVISIONAL


Example:

SELECT down

text becomes:

.


PROVISIONAL CHARACTER RULE
--------------------------

As long as SELECT remains held:

- the same provisional character remains editable
- SELECT combinations REPLACE that character
- they must NOT append new characters
- the provisional position remains fixed as one logical inserted character
- the character may change repeatedly during the same hold

Example:

SELECT down
-> .

while still holding SELECT
-> ?

change selection
-> !

change selection
-> 7

There is still exactly ONE newly inserted character.


SELECT RELEASE
--------------

SELECT released:

- current provisional character becomes committed
- clear the SELECT-session state
- caret remains after the committed character


The conceptual model is:

SELECT down
-> insert "."
-> provisional_position = inserted character

while SELECT held:
    replace provisional character as controls change/cycle

SELECT released:
-> commit current character
-> provisional_position = none


SELECT is therefore:

"open one special-character selection session"

Releasing SELECT commits exactly one character.

19. SELECT + LETTER CHORD — INTERNATIONAL ALTERNATE LETTERS
=======================================================================

SELECT also acts as an international alternate-character modifier.

While SELECT remains held, entering a normal valid letter chord selects an alternate version of that BASE LETTER.

This uses the exact same direction/B/A/R letter geometry as normal typing.


Example:

normal E:

RIGHT + A
= e

= first alternate of E
= é


REPEATING THE FINAL LETTER BUTTON
---------------------------------

Once an alternate-letter family has been selected, repeated presses of the final B/A/R selector while the same relevant letter group remains held cycle through that base letter's alternate characters.

Example E:

hold RIGHT
press A
-> é

press A again while SELECT + RIGHT remain held

press A again
-> ë

press A again
-> ê

press A again
-> é


This is one SELECT session.

Only one provisional character exists.

Each cycle step replaces that character.

-----------------------------

Only these base-letter families require alternate cycles in the first version.

For other base letters:

- a SELECT + letter chord should not insert an unintended normal letter
- leave the provisional character unchanged or use another simple no-op behavior
- do not invent additional accents not listed here


L-LAYER LETTERS
---------------

Alternate characters must also work for letters located on the L layer.

Examples:

N = L + UP + B
S = L + RIGHT + R
U = L + DOWN + A

SELECT + L INTERMEDIATE STATE
-----------------------------

SELECT + L by itself normally cycles common punctuation backward.

However, L is also the second-letter-layer modifier.

Therefore a complete valid SELECT + L + direction + B/A/R letter chord has higher priority than SELECT+L punctuation.

It is acceptable if the provisional character changes temporarily while the user is assembling the chord.

The completed letter chord must replace it with the intended alternate letter.

No extra characters may be created.

20. SELECT INPUT PRECEDENCE / DISAMBIGUATION
=======================================================================

SELECT directional controls overlap physically with the direction groups used by letters.

GENERAL PRECEDENCE
------------------

Within a SELECT session:

1. START commands are not active because START and SELECT should not be treated as simultaneous normal modes.
2. A completed valid letter chord has highest SELECT-input priority.
3. If L + direction + B/A/R forms a valid second-layer letter chord, treat it as that letter.
4. Direction-only input uses number/symbol cycling.
5. R/L without an active valid letter direction group uses common punctuation cycling.
6. All changes affect the same provisional character.


NO DUPLICATE OUTPUT
-------------------

Do not implement SELECT by inserting a new character for every control event.

There must be one provisional character position.

-> "è"

--------------

- START+Up/Down traverses visual rows
- explicit newline and soft wrapping remain distinct
- saving preserves actual text rather than rendered wrapping
- page movement changes viewport while maintaining a valid caret/insertion location
- inserting/deleting near wrap boundaries reflows correctly
- accented UTF-8 characters remain single logical characters for navigation purposes

Prefer deterministic bounded structures suitable for GBA memory.

=======================================================================
27. FILE SAFETY / DATA INTEGRITY
=======================================================================

This is a writer.

Saving integrity matters more than in the read-only GBAReader use case.

Required principles:

- Never truncate/overwrite an existing filename during New File creation.
- Do not advertise a save as complete until filesystem operations succeed.
- Handle write errors visibly.
- Avoid corrupting an existing file if save fails partway, as far as reasonably practical.
- Flush/sync/close correctly using the actual available filesystem API.
- Do not leave stale file handles across menu transitions.
- Loading another file must not silently discard unsaved text.

If the architecture permits a safer temporary-file + replace strategy on this exact hardware/filesystem, evaluate it carefully.

Do NOT introduce a supposedly atomic strategy unless the actual target FatFS/Supercard behavior supports it reliably.

If unsaved edits exist and the user attempts an action that could discard them outside the explicit START+B save-and-return path:

- protect the text
- use a simple confirmation or require save/cancel

Keep this minimal.

30. PERFORMANCE / MEMORY
=======================================================================

Respect Game Boy Advance hardware limits.

Do not solve editing by allocating unbounded whole-file structures.

Determine and document a reasonable maximum editable file size / buffer strategy based on:

- GBA EWRAM
- IWRAM
- renderer usage
- Butano usage
- filesystem buffers
- existing project memory footprint

GBAReader can stream large read-only files.

An editor has different requirements.

Choose an intentional editable-text architecture.

Possible approaches include:

- bounded whole-file buffer if a safe useful size fits
- gap buffer
- piece table
- chunked editable structure
- bounded editable window + rewrite strategy
- another deterministic low-memory approach

Choose based on:

- simplicity
- reliability
- predictable memory
- insertion/backspace responsiveness
- UTF-8 support
- save simplicity

Avoid dynamic-allocation-heavy architecture without a strong reason.

Typing, backspace, cycling SELECT characters, and moving the caret should feel immediate.


=======================================================================
31. INPUT STATE-MACHINE PRIORITY
=======================================================================

Implement explicit state machines.

Do not build input behavior from ad-hoc if-statements that can accidentally overlap.

A useful conceptual priority is:


1. MENU / MODAL UI STATE
------------------------

If in menu/date picker/help/error confirmation:

use that screen's controls.


2. START COMMAND STATE
----------------------

If START is held:

START command semantics have priority.

Do not type normal characters.


3. SELECT PROVISIONAL STATE
---------------------------

If SELECT is held:

all text input modifies the one provisional SELECT character according to the SELECT rules.

Completed valid letter chords take precedence over directional/punctuation intermediate states.


4. ACTIVE LETTER GROUP
----------------------

If D-pad direction is active:

A/B/R select letters.

L may change to second letter layer.

R does NOT act as Shift/Caps while part of a letter chord.


5. ISOLATED R
-------------

If R occurs without a letter group, START, or SELECT:

process Shift/Caps logic.


6. STANDALONE A/B
-----------------

A = Space
B = Backspace


SESSION-BASED LOGIC
-------------------

Keep explicit state for:

- current direction held
- whether L layer is active
- repeated-R count within same DOWN group for G
- repeated-R count within same L+DOWN group for V
- isolated R double-press timing
- pending START state
- whether START command was consumed
- SELECT provisional position
- SELECT current cycle family
- SELECT current alternate-letter base
- SELECT alternate-letter cycle index

Reset session-specific transformations when their defining hold/session ends.

39. FINAL DESIGN PRINCIPLE
=======================================================================

The goal is a tiny, robust, deliberately constrained GBA writing tool whose controls can become muscle memory.

The controller should have a coherent mental model:

A
= Space / second letter selector

B
= Backspace / first letter selector

R
= third letter selector inside a group
= Shift/Caps when isolated

L
= held second alphabet layer

START
= Enter when released alone
= editor command modifier when combined with another control

SELECT
= one provisional special-character session
= numbers
= punctuation
= symbols
= international alternate letters


The intended diary workflow is almost immediate:

turn on GBA
-> A
-> A
-> write

The app should feel like a real controller-native portable writing tool, not a novelty text-entry demo.
